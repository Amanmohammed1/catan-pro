# M2 — Online multiplayer

**Status:** complete

**Goal:** four people on four laptops play a real game, still in 2D.

## Acceptance criteria

| Criterion                                              | Result                               |
| ------------------------------------------------------ | ------------------------------------ |
| Four clients, one full game                            | met, whole-game run in the slow lane |
| A mid-game refresh recovers cleanly                    | met, reconnect by resume token       |
| No hidden information leaks in the network tab         | met, audited byte by byte            |
| Command in, events plus redacted snapshot out          | met, zod-validated at the boundary   |
| Append-only event log keyed by match id                | met, Postgres and in-memory          |
| Turn timer with auto-pass, host kick                   | met                                  |
| Dice fairness: publish sha256(seed), reveal at the end | met                                  |

## Shape

```
packages/protocol   zod schemas for every client message; the wire contract
apps/server         Fastify + ws, rooms, the authoritative Match, persistence
apps/web/src/net    the WebSocket client, lobby, and online session
apps/web/src/game   the shared game screen, used by both modes
```

The client holds nothing but what the server sent it. Hot-seat and online render
through the same `GameScreen`, both fed a redacted view — hot-seat builds one
locally with `playerView()`, online receives one over the socket. Routing both
through the same shape means a redaction bug cannot hide behind "it only matters
online".

### Why the server sends legalMoves

A client holds a redacted view. It does not know the development deck, the other
hands, or the generator state, so it _cannot_ run `legalMoves()` itself. The
server computes the list and sends it down.

That keeps golden rule 3 intact across the network: the UI still derives every
enabled control from legalMoves, it just no longer computes it. A client that
invents an option has it rejected by the reducer anyway, so nothing is trusted
that was not trusted before.

### Persistence

Two tables. `matches` holds the seed and its commitment; `match_commands` is the
ordered log of accepted commands and the events each produced, keyed by match id
with a primary key on `(match_id, seq)`.

What is stored is the command, not just the event. The engine is deterministic,
so seed plus commands reproduces the state byte for byte — which is what makes
restart-from-database work without snapshotting, and it is asserted by a test
that plays a game, reloads the log, replays it, and compares the two states.

Without `DATABASE_URL` the server runs on an in-memory store and says so.

## The leak that was there

Live updates were redacted correctly. The initial snapshot was not: it sent
`match.log` raw, so any player reconnecting received every stolen card and every
development card drawn since the game began — the exact thing golden rule 5
exists to prevent, in the exact place nobody looks.

It was found by a test that reads every byte the server actually sent and
searches for `devDeck`, `rng`, and per-resource opponent hands, rather than
asserting on the shape of the view. That test stays.

## Two things that are not bugs

**The flood limit refuses a fast client.** It sits at 120 messages per second
per socket, raised from 30. Thirty was low enough that a legitimate burst got
refused, which looks exactly like a broken game. A person clicking as fast as
they can manage sends a handful a second.

**Random-legal play runs long.** Games average a few hundred turns, far more
than a real one. That is a property of a bot with no strategy, not of the rules.
Heuristic bots are M9.

## Commands

```bash
pnpm --filter @hexport/server dev    # the game server on :8787
pnpm dev                             # the client on :5173, proxying /ws
pnpm verify                          # lint, typecheck, purity guards, both lanes
pnpm test                            # fast lane, ~13s
pnpm test:slow                       # whole-game runs over real sockets
```

Open two browser windows at `http://localhost:5173`, create a room in one, join
with the code in the other. `?hotseat=1` plays every seat on one screen;
`?debug=1` is the M0 geometry view.

## Known gaps

- Rooms live in the process. A restart loses the lobby; the command log survives
  in Postgres, but nothing reattaches a running room to it yet.
- A kicked player mid-game is disconnected and auto-passed rather than removed,
  because seat numbers key the command log.
- No spectators, no rematch button. Those are M4.
